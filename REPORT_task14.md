## 1. Выявленные проблемы (ключевые)

### P1 — DNS через VPN сломан для всех приложений, кроме нашего (критично)

**Факт (код):** `ProxyVpnService.kt:87–88` назначает TUN DNS `8.8.8.8` и `2001:4860:4860::8888`; `addRoute("0.0.0.0",0)` + `addRoute("::",0)` (строки 84, 86) — весь трафик приложений идёт в TUN.

**Факт (движок):** HTTP-прокси **не умеет UDP**:
```
tun2socks/proxy/http/http.go:83-84
func (h *HTTP) DialUDP(...) (net.PacketConn, error) {
    return nil, errors.ErrUnsupported
}
```
`tunnel/udp.go:29-33`: при ошибке `DialUDP` — `log.Warn` и `return` (сокет закрывается через `defer uc.Close()` на строке 18) — **DNS-ответ приложению не возвращается**.

**Следствие:** классические DNS-запросы UDP/53 приложений → TUN → `ErrUnsupported` → таймаут резолвера. Имя не разрешается → TCP-соединения по доменам не устанавливаются.

**Почему «Тестирование» в приложении может показывать успех:** движок и тестовый сокет работают **в UID нашего приложения**, который исключён из VPN (`ProxyVpnService.kt:89` `addDisallowedApplication(packageName)`) — их DNS/соединения **не входят в TUN**. Тест не моделирует путь Chrome/YouTube.

### P2 — `addDisallowedApplication` и фактический охват VPN

**Факт:** `ProxyVpnService.kt:89` — исключён **только** `com.weathercurrency.app`.

| Приложение | Через VPN? |
|---|---|
| Chrome, YouTube, Telegram и все прочие UID | **Да** → TUN → tun2socks → CONNECT |
| WeatherCurrency (тест, погода, OTA) | **Нет** (напрямую, анти-петля) |

Петля для движка исключена корректно. Но **весь остальной системный DNS и UDP** при этом попадает в нерабочий путь (P1).

### P3 — QUIC/UDP/443 не поддерживается, падение «молчаливое»

**Факт:** `DialUDP` → `ErrUnsupported` → пакеты UDP (QUIC/443, WebRTC, mDNS и т.п.) **отбрасываются без ICMP unreachable** (`tunnel/udp.go:29-33`).

**Гипотеза (подтвердить на устройстве):** Chrome по умолчанию активно использует HTTP/3 (QUIC). При чёрной дыре UDP клиент ждёт таймаут QUIC, затем (не всегда быстро/надёжно) переходит на TCP. Симптом «Chrome полностью не работает» согласуется с **комбинацией P1 (DNS) + P3 (QUIC hang)**, а не только с P3.

**Гипотеза:** YouTube-приложение тянет медиа через домены `*.googlevideo.com` (нужен DNS) и часто предпочитает QUIC → UI открывается (кеш/логин), пайплайн не грузится → «ничего не загружает».

**Гипотеза:** Telegram работает, потому что (проверить на устройстве!) значительная часть координации идёт по кешированным IP/устойчивым DC, клиент агрессивнее ретраит и чаще завершает на TCP; это **не доказательство**, что его DNS проходит корректно.

### P4 — IPv6 полностью введён в VPN, включая DNS-сервер IPv6

**Факт:** `ProxyVpnService.kt:86,88` — маршрут `::/0` и DNS `2001:4860:4860::8888`.

**Риски:**
- Приоритет IPv6 DNS (частый на Android): запрос IPv6/53 → тот же отказ `DialUDP`;
- Если прокси принимает только IPv4 CONNECT — IPv6-назначения (Chrome может предпочитать AAAA) **не работают** (fail-closed, но ощущается как «не работает»);
- Нет `allowFamily`/`setBlocking` и нет логирования утечек IPv6.

### P5 — Private DNS / DoH Chrome не обрабатываются в коде

**Факт:** в `ProxyVpnService` нет обработки Private DNS (DoT TCP/853) и нет влияния на Secure DNS Chrome.

**Гипотезы:**
- Если на устройстве **Private DNS = Automatic/Off** → системный резолвер использует DNS VPN (UDP/53) → сломан (P1).
- Если Private DNS включён (DoT, TCP/853) → может пройти через CONNECT (TCP) — тогда имена резолвятся, и отказ Chrome искать надо в P3/MTU/чём-то ещё.
- Chrome Secure DNS (DoH, обычно TCP/443) **мог** бы пройти через CONNECT; если DoH использует HTTP/3 — снова UDP и P3.

**Без `adb logcat | grep -E 'resolv|Dns|netd|captive'` на устройстве однозначно выбрать вариант нельзя.**

### P6 — Жизненный цикл VPN / смена сети

**Факт:** `startVpn` / `stopVpn` / `onRevoke` / `onDestroy` реализованы (`ProxyVpnService.kt:40–165`); `START_STICKY`.

**Пробелы (анализ, не воспроизведено):**
- Нет `setUnderlyingNetworks`, нет слушателя смены сети → при handover Wi‑Fi↔мобайл TUN может «зависнуть» до ручного переподключения;
- `establish() == null` корректно диагностируется (другой VPN);
- `key.setMark(0)` (`ProxyVpnService.kt:104`) — fwmark не используется; анти-петля держится только на `addDisallowedApplication`.

### P7 — MTU / MSS (вторичная гипотеза)

**Факт:** `setMtu(1500)` (`ProxyVpnService.kt:82`), `key.setMTU(0)` (строка 105) — движок берёт значение по умолчанию при 0, но интерфейс TUN объявляет 1500.

**Гипотеза:** при физическом MTU < 1500 возможны проблемы PMTU для больших TCP-сессий; для HTTP CONNECT внутри TCP это обычно не критично. **Низкий приоритет** без подтверждения пакетами.

### P8 — TCP через CONNECT: код выглядит корректным, E2E не подтверждено

**Факты:** `http.go` — CONNECT + Basic `Proxy-Authorization` (строки 87–127), схемы `http`/`https` (143–144), TLS до прокси с проверкой сертификата (`tls.Client`, `ServerName`, без `InsecureSkipVerify`, строки 58–69).

Приложение: `fd://` + `proxy` (`ProxyVpnService.kt:101–102`), Engine.start (115).

**Не подтверждено на устройстве:** фактические TCP/443 сессии через ваш прокси, таймауты, 407, обрывы.

## 4. Причины отказа Chrome и YouTube (вывод)

Установлено **на уровне кода** (не device E2E):

1. **Имя хоста не разрешается** для UID-ов в VPN: единственный путь DNS — UDP/53 через TUN, а HTTP CONNECT **не умеет UDP** (`http.go:83–84`) и закрывает сессию без ответа (`udp.go:29–33`).  
   → Chrome (свежие запросы DNS) и медиа-домены YouTube → отказ.

2. **QUIC (UDP/443)** отбрасывается тем же кодом; клиенты ждут таймаут HTTP/3 → «зависание» страниц/видео, даже если TCP/443 через CONNECT в принципе работал бы.

3. **IPv6-маршрут `::/0` + IPv6 DNS** добавляют второй «мёртвый» путь (гипотеза H5 — требует проверки).

4. **Не является причиной** (по коду): отсутствие VPN-разрешения, неверный `fd://`, выключение TLS-проверки (проверка включена), неверный Basic-auth в коде CONNECT.

5. **Telegram «работает»** — наиболее вероятно устойчивость клиента (TCP, кеш IP, ретраи); **не доказывает** работоспособность DNS/UDP в VPN.

Отдельно: кнопка «Тестирование» **не валидирует** путь сторонних приложений (сокеты исключены из VPN) — см. P2.

## 5. Ограничения текущего движка (tun2socks v2.7.0 + HTTP CONNECT)

| Возможность | Статус |
|---|---|
| TCP через HTTP CONNECT | ✅ реализовано в коде (E2E не подтверждено) |
| HTTPS-прокси (TLS до прокси) | ✅ (наш патч, проверка сертификатов) |
| Auth Proxy-Authorization | ✅ Basic |
| **UDP вообще (DNS, QUIC, WireGuard…)** | ❌ **протокольный предел HTTP CONNECT** |

| Fake-IP / domain fronting / sniffing SNI | ❌ нет |
| IPv6 | ⚠️ маршруты есть; успех зависит от прокси |
| ICMP/pmtud | ⚠️ gvisor-стек, не исследовался E2E |
| Замена на sing-box | возможна (DNS-модуль, fakeip, TCP/DoH DNS), GPLv3, интеграция сложнее |

**Вывод:** часть проблем — **не баг tun2socks**, а следствие «HTTP CONNECT ≠ полноценный VPN». Часть (DNS-интерцепция, fail-fast UDP, IPv6 policy) можно закрыть доработкой движка/настроек **без** замены. Полная прозрачность UDP невозможна через HTTP CONNECT.

## 6. Рекомендуемая архитектура исправления

**Принципы:** не прятать обход Chrome/YouTube мимо прокси; сохранить HTTPS-проверку; честные ограничения в UI.

### 6.1 DNS (приоритет 1)
**Цель:** приложения получают ответы на UDP/53, не полагаясь на UDP через прокси.

Вариант A (без смены движка — на стороне приложения, сложнее): свой DNS-прокси… **не рекомендуется** (нужен доступ к TUN-пакетам).

Вариант B (**рекомендуется**): доработка tun2socks (движок уже патчили, MIT):
1. **Fake-DNS / hijack UDP/53**: на запрос из TUN отвечать локально; резолвить имена **внутри движка** через TCP DNS (`CONNECT 8.8.8.8:53` или `dialer` TCP) либо DoH (HTTPS POST), затем прозрачно работать по доменам через TCP CONNECT (соединение к хосту по IP после локального резолва — как это делают многие прокси-VPN).
2. Альтернатива: SOCKS5 `UDP ASSOCIATE` — **невозможна**, у пользователя HTTP-прокси.

Вариант C (смена движка): **sing-box** — встроенный DNS (UDP/TCP/DoH), fakeip, сниффинг доменов → TCP CONNECT по домену. Сохраняет HTTP outbound. Лицензия GPLv3 — юр. вопрос, интеграция через AAR/library тяжелее, чем текущий AAR.

### 6.2 TCP через CONNECT (приоритет 2)
- Оставить текущий код CONNECT (он структурно верный).
- Добавить **health-check при подключении** (как ProxyTester, но **внутри** движка/после establish, с DNS через новый модуль): при отказе — UI-состояние «прокси недоступен», не «Подключено».
- Таймауты/keep-alive на стороне движка — исследовать `SetKeepAlive` (есть), выставить осознанные read/write deadlines.

### 6.3 UDP/QUIC (приоритет 2)
- **Явная политика:** UDP через HTTP CONNECT **не поддерживается** (уже в UI).
- Улучшить диагностику: при `DialUDP` error — лог + (желательно) fail-fast для приложений (в движке: ответ/закрытие так, чтобы клиенты быстрее падали на TCP; полный ICMP нереалистичен в TUN-стеке без прав).
- Не «чинить» Chrome отключением VPN для Chrome — это скрытый обход.

### 6.4 IPv4/IPv6 (приоритет 3)
- Опция A: убрать `::/0` и IPv6 DNS, оставить IPv4-only (проще, меньше чёрных дыр при IPv4-прокси).
- Опция B: оставить IPv6, но **отключать IPv6-маршруты**, если прокси не отвечает на CONNECT к IPv6 (A/B на устройстве).
- Добавить логирование фактического семейства в CONNECT.

### 6.5 Chrome/YouTube (приоритет 1–2)
- После DNS (6.1): TCP/443 через CONNECT должен работать; QUIC будет деградировать до TCP — допустимо, **задокументировать**.
- Проверка: Chrome с выключенным QUIC, затем с включённым.

### 6.6 Можно ли остаться на tun2socks?

| Вариант | Оценка |
|---|---|
| **Остаться + доработка DNS/fail-fast/IPv6** | ✅ **рекомендуется**, если готовы патчить Go-движок (уже есть опыт сборки AAR) |
| Замена на sing-box | ⚠️ нужна, только если требуется полноценный DNS/fakeip/UDP-политика «из коробки» и готовы к GPLv3 и новой интеграции |
| Ничего не менять | ❌ Chrome/YouTube не починятся (P1+P3 структурные) |

**Вердикт:** текущий tun2socks **достаточен для TCP-проксирования**, но **без доработки DNS не пригоден как системный VPN** для Chrome/YouTube. Замена движка — **не обязательна** на первом этапе; приоритет — DNS-интерцепция + честная политика UDP/IPv6.

## 7. План тестирования на реальном Android

**Не выполнялось** (нет устройства/logcat в среде задачи).

1. **Baseline с VPN выкл:** `ping`, `nslookup google.com`, Chrome, YouTube, Telegram.
2. **VPN вкл + logcat:**  
   `adb logcat -v time | grep -iE 'ProxyVpn|tun2socks|UDP\]|resolv|netd|Chrome|QUIC'`  
   Искать: `[UDP] dial … unsupported`, ошибки резолвера, отсутствие `lookup` успехов.
3. **DNS:** из Termux/adb shell: `nslookup youtube.com` при VPN — если таймаут → P1 подтверждён.
4. **Private DNS:** `settings get global private_dns_mode` / `private_dns_specifier`; попробовать Automatic vs Off — сравнить Chrome.
5. **QUIC A/B:** Chrome → `chrome://flags/#enable-quic` off/on — влияние на «не работает».
6. **TCP/443:** `curl -v https://www.google.com` (из приложения **не** выйдет — UID в VPN; лучше `tcpdump`/прокси-логи или curl в приложении, исключённом из VPN только для сравнения) + включение CONNECT в логах прокси.
7. **IPv6:** `curl -6` / отключение маршрута `::/0` (после правки) — A/B для Chrome.
8. **Смена сети:** Wi‑Fi→мобайл, проверка живости TUN.
9. **Telegram/YouTube/Chrome** — повтор симптомов после каждого пункта.
10. **Уведомление/жизненный цикл:** свайп сервиса, `onRevoke` с другим VPN.

Критерий успеха после исправлений: резолв доменов в VPN, загрузка страниц Chrome, видео YouTube, при этом трафик этих приложений **проходит через прокси** (проверить по логам CONNECT на стороне прокси).

| Сценарий | Замена нужна? |
